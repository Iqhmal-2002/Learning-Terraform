## 2026-11-19: Refresh, -refresh-only, drift
### What I did
- Went through what refresh updates, when it gets saved, and how to handle drift
### What broke or confused me
- Refresh only touches resources already in state (attributes updated, or dropped if deleted). Never adds untracked resources
- plan refreshes in memory only, doesn't write state. apply writes state but also changes infra
- apply -refresh-only = write refreshed state, zero infra changes. Replaces deprecated `terraform refresh`
- Accepting -refresh-only doesn't keep a portal change: next plan still reverts to the HCL. To keep it: update HCL, or lifecycle ignore_changes
- -refresh-only use case = things that read state without refreshing (terraform output, terraform_remote_state), not deciding drift. Review drift with plan -refresh-only
- Same drift shows + in plan -refresh-only (state → cloud) and - in normal plan (cloud → HCL)
- Import works on whole resources only; a tag is an attribute → edit the HCL, no import. (Exception: things with their own resource type, e.g. aws_ec2_tag)

## 2026-11-18: Terraform plan vs apply, and how state works
### What I did
- Checked whether main.tf (Azure VM + AWS EC2) would provision
- terraform validate failed: file("~/.ssh/id_rsa.pub"), no key existed. Generated one with ssh-keygen; plan then worked
- Learned what each stage checks: validate (local), plan (local checks + read-only API calls), apply (write calls)
- Learned the three things Terraform compares: HCL (desired), state (Terraform's record), cloud (actual)

### What broke or confused me
- Thought plan only used what init downloaded and never called the API. Actually init only downloads provider plugins; plan uses them to make read calls (refresh of resources in state + data sources)
- Errors like a name already taken, AMI not existing, or quota only show up at apply, because those come back from create requests
- Thought state says what "should" exist. It records what Terraform last saw; refresh updates it before comparing to the HCL
- Removing a block from HCL while the resource still exists = plan destroys it
- Thought "HCL is source of truth" meant Terraform would delete anything not in HCL. It only acts on resources in HCL and/or state; a portal-made resource is in neither, so it's invisible to Terraform
- Thought plan would catch a name clash with a portal-made RG. It can't: no state entry means no read call, so plan shows "create" and apply fails with "already exists, needs to be imported"
- Import = putting an existing resource into state so Terraform manages it (import block / terraform import)
- plan never checks if a new resource's ID already exists (shows id = known after apply). apply's create step builds the ID from config (Azure ID = path + name), reads it, and errors if found
- Azure creates are "create or update"; azurerm deliberately refuses to take over an existing resource without import
