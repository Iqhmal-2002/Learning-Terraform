## 2026-10-07 — remote-exec working (finally)

**What I did:**
Got remote-exec working in `Freecodecamp_Terraform/010_provisioners/main.tf`. Built the full VM chain by hand: RG → VNet (10.0.0.0/16) → subnet (10.0.1.0/24) → public IP (Static, Standard) → NSG (allow TCP 22 from my IP only) → NIC → NIC/NSG association → Linux VM with SSH key, `connection` block and `remote-exec`.
Ran `hostname`, `uptime` and `echo > /tmp/hello.txt`, saw the `(remote-exec)` lines in apply, SSH'd in and `cat` the file to confirm. Second apply did nothing because provisioners only run on create. Destroyed everything after.
Ended up on `Standard_D2as_v4` in eastus because nothing cheaper was allowed on my subscription.

**What broke / what confused me:**
- Provisioners are literally just shell commands hooked to a resource's lifecycle. Runs on create (or destroy with `when = destroy`), can use `self.*`, taints the resource on failure, not in plan, not tracked in state. That's why it's a "last resort".
- local-exec runs wherever terraform runs. remote-exec runs wherever the `connection` block points (`host = self.public_ip_address`). Where you put the provisioner decides WHEN it runs and what `self` is.
- SSH keys: public key (padlock) goes on the VM, private key (the key) stays on my laptop because my laptop is the one connecting. `ssh-keygen -t rsa -b 4096`.
- `my_ip` = my laptop's public IP (NSG source). The IP I SSH into = the VM's public IP (`terraform output public_ip_address`). Not the same thing.
- Subnet has to fit INSIDE the VNet range. VNet was /16 not /24, misread it.
- Standard public IP blocks all inbound until an NSG allows it. The portal wizard makes the NSG for you, Terraform doesn't make anything you don't write.
- NSG rule: source port is `*` because the client uses a random ephemeral port. Destination is `*` because Azure already NATs the public IP to the private IP before the NSG checks it.
- ~60 errors on the NIC were from ONE missing quote (`"example{`). Then the subnet/IP settings had to go inside an `ip_configuration {}` nested block.
- `"remote-exec:"` with a colon = "unavailable provisioner". Validate didn't catch it, plan did.
- Nested blocks (`security_rule {}`, `ip_configuration {}`) are sub-parts that can repeat. Only exist where the provider schema says so. `_name` args take `.name`, `_id` args take `.id`.
- Block order in the file doesn't matter, terraform builds a graph from references. Used `depends_on` on the VM so the NSG association is done before SSH.
- VM size hell, 3 different errors:
  - `SkuNotAvailable` = Azure ran out of capacity for that size in that region (B1s in westus2)
  - `OperationNotAllowed ... quota` = my subscription's per-family per-region limit (Basv2 = 0)
  - `NotAvailableForSubscription` = size blocked outright for my subscription (all B1 sizes in mainstream regions)
- Plan passed every time. Capacity/quota/restrictions only get checked at apply.

**What I'd do differently:**
Check what my subscription can actually use BEFORE picking a size/region instead of guessing one at a time:
- `az vm list-usage --location <region> --output table` for quota
- `az vm list-skus --location <region> --resource-type virtualMachines --query "[?name=='<size>']" --output table` for availability (empty = blocked, `--all` shows why)
- Ignore regions with STG/SLV/FRE or weird numbers in the name, they're staging/restricted.
Use references for location so changing region is a one line change (it was).
Look at cloud-init (`custom_data`) next, that's what people actually use instead of remote-exec.
